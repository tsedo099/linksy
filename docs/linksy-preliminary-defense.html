1 · Танилцуулга ба үндсэн боломжууд

Linksy юуг шийдэх вэ, ямар боломжуудтай вэ?

Эхлээд асуудлаас эхэлье. Facebook, Instagram гэх мэт нийгмийн сүлжээнүүд хэрэглэгчийн өгөгдлийг хязгааргүй цуглуулдаг, мөн ямар пост хэнд харагдахыг "нууц алгоритм" шийддэг. Linksy үүний оронд хэрэглэгч өөрөө хэн пост-ыг нь үзэх-ийг (Public, найз, эсвэл "Close circle" гэсэн ойрын тойрог) шийдэх боломжтой. Эрэмбэлэлт нь нууц биш — like + comment-ийн тоо × шинэлэг байдал гэсэн ил тод томьёотой.

Системийн үндсэн 10 боломжийг танилцуулъя:

🎨 Creator Mode + XP оноо

2 пост эсвэл 10 like/comment хүлээн авсан хэрэглэгч идэвхжүүлж болно. Пост бичих=10, like ирэх=2, comment=3, follow=4, өдөр бүр нэвтрэх=5 оноо. Subscription tier-ээс хамаарч оноо үржинэ. Redis-д leaderboard.

📊 Creator Dashboard

Үзэлт, like, comment, save, repost, follow-ийн жинхэнэ статистик. Өмнөх 7/30/90 хоногтой харьцуулсан өсөлт хувиар. Өдрийн график, шилдэг 5 пост.

🔐 Authentication

Email + нууц үгээр бүртгэх/нэвтрэх. Token нь 15 минут тутамд солигдох (security), 2FA код, email баталгаажуулалт, нууц үг сэргээх, олон удаа буруу оруулбал түр түгжих.

📰 5-н горимтой Feed

For You (бүгд), Friends (зөвхөн дагасан), Close circle (ойрын тойрог), Creator (creator-ууд), Discover (алгоритмаар сонгогдсон шинэ хүмүүс).

📸 Пост & Story

1-4 зураг/видео, санал асуулга, цаг товлох, draft, цомог, comment модераци, хамтран зохиогчид, hashtag/mention, харааны бэрхшээлд зориулсан alt бичиг заавал.

💬 Бодит цагийн чат

1-1 эсвэл group чат, live шинэчлэлт, "бичиж байна..." indicator, унших баталгаа, дуут мессеж, тогтоосон хугацаа өнгөрсний дараа арилах мессеж.

🔒 End-to-End шифрлэлт

Мессеж зөвхөн илгээгч/хүлээн авагч хоёрт уншиж болохуйц. Сервер plaintext харахгүй — зөвхөн шифрлэгдсэн ciphertext хадгалдаг. Хувийн түлхүүр browser-аас гадагш гарахгүй.

📞 Дуу/Видео дуудлага

WebRTC — медиа stream нь peer-to-peer (хэрэглэгч хооронд шууд), сервер дамждаггүй. NAT-ийн ард байгаа хэрэглэгчдэд coturn TURN сервер ашигладаг.

🔔 Гурван суваг Push

Browser, Android (FCM), iOS (APNs) — гурван өөр платформд нэг систем мэдэгдэл илгээдэг. Хэрэглэгчийн "чимээгүй цагийн" тохиргоог хүндэтгэнэ.

🌍 6 хэл + GDPR + Хяналт

Англи, Монгол, Хятад, Япон, Солонгос, Араб (баруунаас зүүн). Cookie consent banner, өгөгдлөө татаж авах эрх. Алдааг Sentry-р барих, лог-ыг pino-р цуглуулах.

Дараагийн алхамд систем хэрхэн зохион байгуулагдсаныг тайлбарлая. Next.js App Router нь сервер болон клиент хоёрыг нэг кодын баазад нэгтгэн ажиллуулдаг тул хоёр серверийг тусдаа deploy хийх шаардлагагүй. Шифрлэгдсэн мессеж 4 алхмаар явагддаг

1

Хувийн түлхүүр үүсгэх

Хэрэглэгч browser-ээрээ нийтийн (public) болон хувийн (private) хоёр түлхүүр үүсгэдэг. Зөвхөн нийтийн түлхүүрийг л серверт илгээнэ. Хувийн түлхүүр browser дотроос гадагш гарахгүй.

2

Хоёр хүний хооронд нууц утга тохирох

Илгээгч нөгөө хүний нийтийн түлхүүрийг авна. Дараа нь хоёр хүний түлхүүрүүдийг хольж зөвхөн тэр хоёрт мэдэгдэх нэг ижил нууц утга-ыг гаргаж авдаг. Энэ нь сервер хэзээ ч мэдэхгүй утга.

3

Мессежийг шифрлээд илгээх

Илгээгч мессежээ тэр нууц утгаар шифрлээд серверт илгээнэ. Сервер задлахгүй — гарын үсэг шиг харагдах ciphertext-ийг л харна. Хэрэв client алдаагаар plaintext илгээвэл сервер шууд "" болгоно.

4

Хүлээн авагчид хүргэх ба задлах

Сервер шифрлэгдсэн мессежийг хүлээн авагчид яаралтай хүргэнэ (SSE-ээр). Хүлээн авагч өөрийн хувийн түлхүүрээрээ задлаж жинхэнэ мессежийг уншина.

3 · Ашигласан технологи — яагаад сонгосон бэ?

Tech stack ба сонголтын үндэслэл

Энэ хэсэгт ашигласан технологи бүрийг яагаад сонгосноо тайлбарлая. Технологийн нэрийг жагсаах нь хангалтгүй тул сонголтын логикоо тэр чигээр нь танилцуулна:

Next.js 16frontend + backend

Яагаад: Хуудас (frontend) болон API хоёрыг нэг кодын дотор бичиж нэг газар deploy хийнэ. Хоёр өөр сервер удирдах шаардлагагүй. Бүх API дээр auth, CSRF, rate-limit зэргийг middleware нэг газар хэрэгжүүлнэ.

React 19 + TypeScriptUI бүтэц

Яагаад: React нь UI-г жижиг, давтан хэрэглэх боломжтой component-ууд болгож хуваадаг. TypeScript нь алдааг код хийж байх үед барьдаг учраас том төсөлд refactoring аюулгүй болно.

PostgreSQL 16үндсэн өгөгдлийн сан

Яагаад: Хэрэглэгч ↔ пост ↔ комент гэх мэт олон харилцан холбоотой өгөгдөлд таарна. Олон үйлдлийг нэг "atom" болгож хэрэв нэг нь алдвал бүгдийг буцаах боломжтой. Аналитикт зориулсан хүчирхэг SQL функцуудтай.

Prisma 7ORM (DB ↔ код гүүр)

Яагаад: Schema файлаас TypeScript type-уудыг автоматаар үүсгэдэг. Хэрэв DB schema өөрчлөгдвөл код шууд алдаа заана. Migration-уудыг хянахад CI дээр автомат шалгалт хийнэ.

Redisхурдан санах ой

Яагаад: Гурван өөр ажилд нэг систем: (1) олон удаа нэвтрэх оролдлогыг тоолох, (2) олон сервер хооронд real-time event дамжуулах, (3) Creator XP-ийн leaderboard. Бүгд миллисекундын хурдтай.

BullMQbackground ажлууд

Яагаад: Email илгээх, цэвэрлэгээний cron гэх мэт удаан ажлуудыг HTTP хүсэлтээс салгаж тусдаа процессоор гүйцэтгэдэг. Алдаатай ажлыг автоматаар дахин оролддог.

WebRTC + coturnдуу/видео дуудлага

Яагаад: WebRTC нь медиа stream-ийг хэрэглэгч хоёр хооронд шууд дамжуулдаг тул сервер дамждаггүй — bandwidth идэхгүй. NAT-ийн ард байгаа хэрэглэгчдэд coturn TURN сервер нь "гүүр" хийж өгдөг.

Web Crypto APIшифрлэлтийн алхам

Яагаад: Browser-т өөрөө шингэсэн API учраас тусдаа library суулгах шаардлагагүй, build хэмжээг өсгөхгүй. Шифрлэлтийн алгоритмуудыг компьютерийн hardware-аар хурдан гүйцэтгэдэг.

3 · Технологи (үргэлжлэл)

Бусад чухал сонголтууд

Үргэлжлүүлэн validation, real-time push, observability, deployment талын сонголтуудаа тайлбарлая:

Zodоролтын шалгалт

Яагаад: Хэрэглэгчийн API руу илгээх өгөгдлийг бүгдийг нэг газар (schema-аар) шалгадаг. Frontend form ба backend нэг ижил schema reuse хийдэг тул хоёр газар адил дүрэм бичих шаардлагагүй.

Zustandclient state

Яагаад: Redux-ээс хамаагүй хөнгөн (1KB), бараг код бичихгүйгээр state удирдана. Жижиг store-уудад (theme, notification) хангалттай.

VAPID · FCM · APNspush мэдэгдэл

Яагаад: Гурван өөр платформ — browser (VAPID), Android (FCM), iOS (APNs) — тус бүрд тусгай суваг ашигладаг. Бид гурвыг нэг dispatcher-аар нэгтгэснээр feature код суваг бүрийн дэлгэрэнгүйг мэдэх шаардлагагүй.

Server-Sent Eventsсервер → client live

Яагаад: WebSocket-ийн оронд SSE-ийг сонгосон. SSE нь HTTP дээр явдаг тул firewall-аар амар, автомат дахин холбогддог. Бид зөвхөн сервер→client чиглэлд мессеж явуулна — хоёр чиглэлтэй WebSocket хэрэггүй.

DOMPurifyXSS халдлага хамгаалалт

Яагаад: Хэрэглэгчийн илгээсэн HTML (rich-text comment гэх мэт) дотор аюултай script байж болзошгүй. DOMPurify нь HTML-ийг "цэвэрлэж" зөвхөн зөвшөөрсөн tag-уудыг үлдээдэг.

Sharp + ffmpegзураг/видео боловсруулалт

Яагаад: Зургийг WebP формат руу шилжүүлэн хэмжээг 60-70% багасгана. Видеоны thumbnail (хавтасны зураг) автомат үүсгэнэ. Хоёул native binary учраас Node-ийн main thread-ийг саатуулахгүй.

Sentry + pinoалдаа & лог

Яагаад: Sentry — production дээр гарсан алдааг автоматаар alert-той цуглуулна. Pino — JSON формат лог, дэлхийн хамгийн хурдан Node logger-уудын нэг — server-т ачаалал бараг өгөхгүй.

Docker + Composeорчны нэгдмэлжилт

Яагаад: "Энэ миний компьютер дээр ажиллана" гэдэг асуудлыг шийднэ. docker compose up гэсэн нэг команд нь app, PostgreSQL, Redis, coturn зэрэг бүх системийг нэгэн зэрэг ажиллуулна.

Token-based verify (24ц TTL), нууц үг сэргээх (60 мин TTL), Resend/SendGrid + React-email template (welcome/verify/reset/login-alert/digest).

Refresh token rotation

15-мин access JWT + opaque refresh (SHA-256 hash) 30-day sliding window. Ашигласан бүрт шинэ refresh issuance. Logout → revoke.

Brute-force lockout

Redis rate-limit (IP 40/15мин + identifier 5/1мин), 5 буруу нууц → 15 мин account lockout (`User.failedLoginAttempts/lockedUntil`), 429 + Retry-After.

Password policy + Common blocklist

Том+жижиг+тоо+тэмдэгт заавал, 8-128 урт, дахигдах тэмдэгт хориглох, 1000+ "password123", он+суурь хэв маяг бүхий Set blocklist.

Session list + revoke

Идэвхтэй device-уудын жагсаалт (IP + UA + ipgeo + lastSeen) + remote revoke. "Sign out other sessions" Settings-д.
